# Official TOON 4.4 vs custom 4.4

**Custom 4.4 keeps shared table columns when records also contain collections or fields that vary
between rows.** This reduces repeated field names without requiring you to flatten your models.
Choose it for compatible producers and consumers that exchange nested catalogs, stock records,
audit histories or similar collections. Choose official 4.4 when consumers require the standard grammar.

This guide covers **DevOp.Toon 0.3.0**, **Core 0.2.0**, **API 0.2.0** and **Client 0.2.0**.
`4.4` is a protocol version; it is separate from the NuGet package version.

## What changes, and why?

Official 4.4 already supports nested header groups and keyed tables. Those features are shared
by both profiles. The custom extension addresses rows that cannot fit a complete shared header:
it keeps the eligible columns and writes the remaining fields one level beneath their owning row.
These fields are called **row spills**.

| Behavior | Official `V4_4` | `CustomV4_4` |
| --- | --- | --- |
| Uniform scalar rows | Shared table header | Shared table header |
| Uniform nested objects | Nested header groups | Nested header groups |
| Uniform object-valued maps | Keyed tables | Keyed tables |
| Rows containing array-valued fields | List form | Shared columns plus row spills, when eligible |
| Rows with different fields or irregular nested objects | List/nested form | Shared columns plus row spills, when eligible |
| Keyed entries with collections or irregular fields | Nested object form | Keyed table plus entry spills, when eligible |
| No eligible shared columns | List/nested form | List/nested form |
| Omit null/empty values by default | Both omission options `false` | Both omission options `true` |
| Annotation keys (`@id`, `$ref`, `@odata.context`, `Raven-Clr-Type`) | Quoted | Unquoted |
| Column with the same value in every row | Repeated in each row | Repeated, or once in the header with `ConstantColumns` |
| Transport version value | `4.4` | `custom-4.4` |

Official grammar and examples are documented in the
[TOON format overview](https://toonformat.dev/guide/format-overview).
The row-spill extension requires a custom-compatible reader at both ends.

## The same nested data in both formats

The following output is generated by the [runnable sample](../samples/CustomV44/README.md),
with two-space indentation and both omission options disabled. Both versions preserve the same
DTO values. Each product has an `Id`, a nested `Customer`, and a `Tags` collection.

Official 4.4 uses a list because `Tags` cannot become a primitive table cell:

```toon
[2]:
  - Id: 1
    Customer:
      Name: Ada
      Country: IS
    Tags[2]: a,b
  - Id: 2
    Customer:
      Name: Bob
      Country: GB
    Tags[1]: c
```

Custom 4.4 keeps `Id` and the uniform `Customer` group in the header, with `Tags` below its row:

```toon
[2]{Id,Customer{Name,Country}}:
  1,Ada,IS
    Tags[2]: a,b
  2,Bob,GB
    Tags[1]: c
```

The cells follow the header's depth-first order: `Id`, `Customer.Name`, `Customer.Country`.
Spills belong to the preceding row, so the nested collections keep their original owner. This
layout saving does not depend on dropping empty or null values.

If `Tags` is removed, both profiles can emit the same nested table:

```toon
[2]{Id,Customer{Name,Country}}:
  1,Ada,IS
  2,Bob,GB
```

### Keyed collections

For a dictionary of products, custom 4.4 also keeps the entry keys alongside the shared columns:

```toon
[2:]{Id,Customer{Name,Country}}:
  sku-1: 1,Ada,IS
    Tags[2]: a,b
  sku-2: 2,Bob,GB
    Tags[1]: c
```

DevOp.Toon 0.3.0 quoted these entry keys (`"sku-1":`); from 0.4.0 custom 4.4 writes them
unquoted, as described under [annotation keys](#annotation-keys).

The colon in `[2:]` identifies a keyed table. Each entry row starts with its dictionary key;
its spills appear one indentation level deeper. Keyed tables need at least two nonempty
object-valued entries and at least one eligible shared leaf. Arrays of objects need at least
one eligible shared leaf. Otherwise the encoder uses the ordinary nested/list form.

## Constant columns

In releases after DevOp.Toon 0.4.0, setting `ToonEncodeOptions.ConstantColumns = true` with
`CustomV4_4` writes a column whose value is the same in every row once, in the table header, as
`Name=value`. The rows then carry only the columns that vary. The
[protocol version sample](../samples/ProtocolVersions/README.md) prints this output:

```toon
[3]{CompanyId=acme,IsSystem=false,CreatedBy=system,AccountCode,Name,AccountType}:
  6900,Other Expenses,Expense
  1000,Cash,Asset
  2000,Payables,Liability
```

Without the option the same table repeats `acme,false,system,` on every row. Decoding gives every
row the header value, exactly as if each row had held it in a cell.

- **Opt-in and custom-only.** The option defaults to `false`. Every other protocol version ignores
  it, and its output is byte-for-byte unchanged.
- **When a column becomes a constant.** The table needs at least three rows, and the column must be
  present in every row with the same written value. Values must also share a type: `1`, `1.0` and
  `"1"` are different, as are `DateTime` values that differ only in `Kind`, `DateTimeOffset` values
  for the same instant with different offsets, and `Uri` values that differ only in the fragment.
  A column missing from some rows is written as a row spill, as before.
- **Every table keeps a cell.** If every column would be constant, the first leaf column in header
  order stays a cell, so each row still has a line.
- **Nested groups and keyed tables.** Leaves inside a nested group can be constants
  (`{Id,Customer{Country=IS,Name}}`), and keyed tables keep their entry keys and spills.
- **Nulls and empty strings.** With `IgnoreNullOrEmpty = true`, a top-level column that is null or
  empty in every row is still omitted first. Otherwise it is written as `Note=null` or `Tag=""`. A
  column that mixes null and `""` is not a constant.
- **Quoting.** A header value is quoted wherever a cell would be, and also when it contains `=`,
  `,`, `|`, a tab or header punctuation: `Expr="a=b"`, `Pair="x,y"`. Only the first unquoted `=`
  in a field separates the name from the value; a quoted name such as `"a=b"` remains an ordinary
  column.

The decoders in this release always accept constant columns in `CustomV4_4` input. `Auto`
detection treats an unquoted `=` inside a header field list as custom 4.4, since no other encoder
writes one. Hand-written official input that uses such an unquoted field name, for example
`[2]{a=b,c}:` with two cells per row, was decoded by `Auto` in 0.4.0 but now fails with a
row-width error; decode it with an explicit official `ProtocolVersion`, which still reads `a=b` as a
field name. Readers from DevOp.Toon 0.4.0 and earlier cannot read this output: under `CustomV4_4`,
`V4_4` or `Auto` they reject it with a row-width error, and an explicit `V4_0` to `V4_3` non-strict
reader can bind the cells to the wrong columns. Turn the option on only when every reader has
been updated.

## Annotation keys

JSON gives `@` no special meaning, but several conventions build on it: JSON-LD keywords
(`@context`, `@id`, `@type`), OData annotations (`@odata.context`, `Name@odata.type`) and
RavenDB metadata (`@metadata`, `@collection`), as do `System.Text.Json` reference
preservation (`$id`, `$ref`, `$values`) and JSON Schema (`$schema`). Official 4.4 can carry them, but its key grammar
`[A-Za-z_][A-Za-z0-9_.]*` forces quotes. Custom 4.4 writes them unquoted:

```toon
@id: accounts/6900
Name: Other Expenses
@metadata:
  @collection: Accounts
  Raven-Clr-Type: "Contoso.Billing.Account, Contoso.Billing"
  @flags: HasRevisions
```

An unquoted custom 4.4 key may also contain `@` and `$` anywhere, and `-` anywhere except the first
character, so it cannot be read as a list item. Any other key keeps the official rule and is
quoted when needed. The 4.x profiles support neither path expansion nor key folding, so a dotted
annotation key such as `@odata.context` always stays one key.

Bind annotation keys to DTO members with `[ToonPropertyName("@id")]`, or decode the document
as `ToonNode` or `Dictionary<string, object?>`.

### Keep unknown keys with `[ToonExtensionData]`

From **DevOp.Toon 0.4.0** with **Core 0.3.0**, a DTO can keep annotation keys it does not model.
Mark one `IDictionary<string, object?>` or `Dictionary<string, object?>` property:

```csharp
public sealed class Account
{
    public string? Name { get; set; }

    [ToonExtensionData]
    public IDictionary<string, object?>? Annotations { get; set; }
}
```

Decoding captures every key without a matching member; encoding writes the entries after the
declared members, as siblings:

```toon
Name: Other Expenses
@id: accounts/6900
@metadata:
  @collection: Accounts
```

- In 0.4.0 it applies to the 4.x profiles only (official 4.0 to 4.4 and custom 4.4); `V3_0` and
  `CustomLegacy` write the dictionary as a nested object and capture nothing. After 0.4.0 the
  legacy profiles flatten and capture too. A 0.4.0 legacy document's nested dictionary now decodes
  as a single entry named after the property; see
  [extension data in the protocol guide](ProtocolVersions.md#extension-data).
- A member wins: an entry whose key equals a member's TOON name or CLR name is not written.
  For constructor-bound types such as positional records the match ignores case, as decoding does.
- Captured objects become `Dictionary<string, object?>`, arrays `List<object?>`, and numbers
  `double`.
- Entries take part in tables like members do: uniform entries become columns, and other
  entries spill under their row in custom 4.4 (official 4.4 falls back to list items).
- A key naming a declared member that decoding cannot bind, such as a computed getter-only
  property, is skipped rather than captured (0.4.0 captured it).
- `ToonService.Deserialize<T>(body, "application/json")` does not capture keys in 0.4.0; after
  0.4.0 it does, with numbers as `double`.

## Use custom 4.4 without omitting data

Install runtime **0.3.0**; its Core dependency supplies the enum:

```bash
dotnet add package DevOp.Toon --version 0.3.0
```

This complete console example uses explicit versions and matching indentation:

```csharp
using DevOp.Toon;
using DevOp.Toon.Core;

Product[] products =
[
    new() { Id = 1, Customer = new() { Name = "Ada", Country = "IS" }, Tags = ["a", "b"] },
    new() { Id = 2, Customer = new() { Name = "Bob", Country = "GB" }, Tags = ["c"] }
];

var text = ToonEncoder.Encode(products, new ToonEncodeOptions
{
    ProtocolVersion = ToonProtocolVersion.CustomV4_4,
    Indent = 2,
    IgnoreNullOrEmpty = false,
    ExcludeEmptyArrays = false
});
var decoded = ToonDecoder.Decode<Product[]>(text, new ToonDecodeOptions
{
    ProtocolVersion = ToonProtocolVersion.CustomV4_4,
    Indent = 2
})!;
Console.WriteLine(text);
Console.WriteLine(decoded[0].Customer.Name);

public sealed class Product
{
    public int Id { get; set; }
    public Customer Customer { get; set; } = new();
    public string[] Tags { get; set; } = [];
}

public sealed class Customer
{
    public string Name { get; set; } = "";
    public string Country { get; set; } = "";
}
```

Custom modes default `IgnoreNullOrEmpty` and `ExcludeEmptyArrays` to `true`. Set both explicitly
to `false` when null, empty-string and empty-array distinctions matter. Enabling omissions is a
separate choice that can change the represented data. Typed decoding preserves the fields in
your supported DTO schema; use DOM/JSON paths when retaining unmodeled JSON members matters.

Changing both enum selections to `V4_4` uses the official grammar. The encoder chooses the
eligible layout; selecting custom does not force every collection into a table.

The [full sample](../samples/CustomV44/README.md) uses published NuGet packages, prints both
layouts and checks complete typed round trips, dictionary keys, nulls and empty values.

## ASP.NET Core and HTTP clients

With **DevOp.Toon.API 0.2.0**, configure MVC response encoding while leaving request decoding
at `Auto`, so a supplied request `X-Toon-Version` can select the body grammar:

```csharp
using DevOp.Toon.API;
using DevOp.Toon.Core;

builder.Services.AddControllers().AddToon(options =>
{
    options.Indent = 2;
    options.Encode.ProtocolVersion = ToonProtocolVersion.CustomV4_4;
    options.Encode.IgnoreNullOrEmpty = false;
    options.Encode.ExcludeEmptyArrays = false;
});
```

`builder` is your ASP.NET Core application's existing builder. This is MVC formatter registration;
map your controllers in the application as usual.

With **DevOp.Toon.Client 0.2.0**, request custom responses independently of the request format:

```csharp
using DevOp.Toon;
using DevOp.Toon.Client;
using DevOp.Toon.Core;

builder.Services.AddToonClient(options =>
{
    options.BaseAddress = new Uri("https://api.example.com/");
    options.EncodeOptions = new ToonEncodeOptions
    {
        ProtocolVersion = ToonProtocolVersion.V4_4,
        Indent = 2
    };
    options.ResponseEncodeOverrides = new ToonResponseEncodeOverrideOptions
    {
        ProtocolVersion = ToonProtocolVersion.CustomV4_4,
        Indent = 2,
        IgnoreNullOrEmpty = false,
        ExcludeEmptyArrays = false
    };
});
```

For raw HTTP clients, the corresponding request headers are:

```http
Content-Type: application/toon
Accept: application/toon
X-Toon-Version: 4.4
X-Toon-Option-ProtocolVersion: custom-4.4
X-Toon-Option-Indent: 2
X-Toon-Option-IgnoreNullOrEmpty: false
X-Toon-Option-ExcludeEmptyArrays: false
```

Here the request body is official 4.4, while the requested response is custom 4.4. A TOON response
declares its actual body version in `X-Toon-Version`. To send a custom request body as well, set
the client's `EncodeOptions.ProtocolVersion` to `CustomV4_4` and explicitly disable its two
omission options; raw HTTP senders use `X-Toon-Version: custom-4.4` with a matching body.
For GET requests without a body, omit the body headers (`Content-Type` and `X-Toon-Version`).

Automatic decoding can recognize distinctive custom syntax, but many documents are valid under
multiple versions. Use the known body version or transport metadata; detection does not prove
the producer's exact version. `Auto` is decode-only. Do not add a version directive to TOON text.

## Measured benefits and tradeoffs

The **6 November 2026** published-package benchmark measured all **2,051 normalized product DTOs**
on **.NET 10.0.13**, with omissions disabled in both profiles:

| Metric | Official 4.4 | Custom 4.4 |
| --- | ---: | ---: |
| UTF-8 payload bytes | 5,959,545 | 2,939,907 |
| Bytes allocated during decoding | 27,730,160 | 10,242,568 |
| Encode median, ms | 28.23 | 19.98 |
| Explicit decode median, ms | 62.35 | 43.51 |

On this dataset, custom output contains **50.7% fewer UTF-8 bytes** and decoding allocates
**63.1% less memory**. Both profiles preserve the same complete normalized DTO model.
The measurement uses 30 warmups and 50 samples, tiered compilation disabled, and no forced GC
inside timed samples. Profiles ran sequentially in one process, so shared-pool history can
affect timing and allocation observations. This is a measured workload, not a general speed guarantee.

The DTO projection excludes the original JSON's `Publication` member; a separate raw-DOM checker
covers that member. These results measure typed serialization, not full raw-JSON preservation,
HTTP latency, retained memory or LLM token counts. Smaller UTF-8 output does not establish a
specific token saving. Compression results also need their own comparison.

Compared with **legacy custom**, a separate fresh-process old/new pair found custom 4.4 decoded
**17.0% slower**, allocated **42.1% less memory during decoding**, and produced **3.9% fewer bytes**.
The older encoder also has a reported numeric precision defect. These are different comparisons;
custom 4.4 is not a speed upgrade for every existing workload.

### Constant columns

A size-only comparison on **11 November 2026** (.NET 10.0.14, local runtime build, `Indent = 1`, comma delimiter)
encoded the same 2,051 product DTOs and a synthetic chart of accounts with and
without `ConstantColumns`. The accounts dataset has 1,000 deterministic rows whose company, currency,
status, audit and opening-balance fields are the same for every row, while code, name, type and VAT
code vary. Gzip and Brotli use `CompressionLevel.Optimal`. Every lossless profile round-tripped its
complete typed model.

| Dataset and profile | UTF-8 bytes | Gzip bytes | Brotli bytes |
| --- | ---: | ---: | ---: |
| Products, custom 4.4 lossless | 2,939,907 | 371,233 | 326,843 |
| Products, custom 4.4 lossless + constants | 2,817,346 (-4.2%) | 373,127 (+0.5%) | 327,823 (+0.3%) |
| Products, custom 4.4 compact | 2,547,079 | 362,284 | 320,527 |
| Products, custom 4.4 compact + constants | 2,426,532 (-4.7%) | 362,164 (-0.0%) | 319,626 (-0.3%) |
| Accounts, custom 4.4 lossless | 113,529 | 7,495 | 3,362 |
| Accounts, custom 4.4 lossless + constants | 44,598 (-60.7%) | 6,624 (-11.6%) | 3,134 (-6.8%) |
| Accounts, custom 4.4 compact | 108,518 | 7,490 | 3,319 |
| Accounts, custom 4.4 compact + constants | 44,582 (-58.9%) | 6,611 (-11.7%) | 3,117 (-6.1%) |

Constant columns cut uncompressed size substantially when many columns repeat, but gzip and
Brotli already remove most of that repetition: on the product fixture the compressed payloads
became slightly larger. Expect the benefit mainly where payloads are not compressed, or for
wide tables with many row-invariant columns. Encoding with the option on allocated 7,094,544
bytes for the product fixture against 7,213,952 bytes with it off, while decoding allocated
10,353,880 bytes against 10,243,488 (+1.1%), because more distinct header texts reach the
header caches; timings on the shared
measurement machine varied too much between runs to report a speed difference. The
[protocol benchmark harness](../benchmarks/DevOp.Toon.ProtocolBenchmarks/README.md) reproduces
these figures with the `custom4.4-constants-lossless` and `custom4.4-constants-compact` profiles.

See [published-package results and reproduction](PublishedPackageBenchmarks.md) for the complete
method, provenance and fidelity limits. For performance budgets, run the equivalent profiles in
isolated fresh processes on your own data, including explicit and automatic decoding separately.

## Choosing a profile

Use **official 4.4** for standard TOON interchange or when all rows already fit its tables.
Use **custom 4.4** when shared scalar/nested columns coexist with collections or irregular fields,
and compatible readers are under your control. Use **CustomLegacy** when you need the earlier
custom wire behavior; custom 4.4 is a separate format, with literal dotted keys and the v4 grammar.
